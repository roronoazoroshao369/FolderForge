# ADR-0012: Mission Control control plane (per-folder provisioner, SPA, Cloudflare publish, agent council)

- Status: Proposed; council session 2026-08-25
- Date: 2026-08-25
- Updated: 2026-08-25

## Context

FolderForge 2.7.9 already provides a governed MCP control surface for one active
workspace: policy-as-code, approvals, audit, Workspace Capsules, task isolation,
workflows, distributed workers, plugins, a verified local marketplace, and a
local Mission Control operator view (`docs/mission-control.md`) that reads the
same runtime `Container` as MCP calls and explicitly does **not** create a
second execution path.

The next product level turns one workstation into an MCP **provisioning and
operations console**: every project folder can become its own governed MCP
server, a full operator UI manages the fleet, and selected endpoints can be
published through authenticated tunnels and static hosting (Cloudflare). A
multi-role agent council drives ongoing discovery and implementation under the
existing policy/approval pipeline.

Hard constraints inherited from existing decisions:

- ADR-0004: OAuth is a resource-server concern; static credentials never act as
  OAuth credentials.
- ADR-0005: distributed execution uses signed identities and explicit replay
  contracts; public hosting remains an operator-controlled action.
- Mission Control today is local-only and single-operator; a remote multi-tenant
  console is explicitly out of scope for that feature.

## Decision

FolderForge grows four coordinated capabilities, in this order. Each ships
behind the normal policy, approval, rate-limit, and audit pipeline; none of them
creates a privileged side channel around the tool registry.

### 1. Per-folder provisioner (`src/provisioner/`)

A provisioner module manages a bounded fleet of FolderForge MCP instances:

- one record per folder: `{ id, projectPath, port, toolsPreset, policyMode,
  auth: { mode, secretRef }, tunnelRef?, createdBy, state }`;
- secrets are generated by the server, stored as **references only**, and never
  returned after creation (same rule as existing token handling);
- lifecycle: `create -> start -> (restart | log-follow) -> stop -> destroy`,
  all executed through the existing `ProcessManager` so Mission Control process
  actions and write-freeze containment keep working unchanged;
- every provisioned instance inherits the workspace boundary of its folder and
  its own allowed-directories list; the parent instance cannot widen them;
- fleet size, port range, and per-instance tool presets are operator-configured
  caps, not agent-controllable arguments.

Agent-facing tools: `provision_create`, `provision_list`, `provision_status`,
`provision_start`, `provision_stop`, `provision_destroy`, `provision_logs`
(start/stop/destroy are HIGH/CRITICAL and approval-gated like other lifecycle
tools today).

### 2. Mission Control SPA (`packages/mission-control`)

The current dashboard serves a minimal operator view. The next step is a
decoupled single-page application (Vite + React, TypeScript) that talks to the
dashboard HTTP API only:

- screens: Workspaces/Fleet, Approvals, Live calls, Audit, Tunnels, Plugins &
  Marketplace, Council runs;
- authentication: paste-token flow for loopback development; OAuth mode reuses
  the ADR-0004 resource server — the SPA never receives a new credential type;
- the existing redacted `GET /mission-control` snapshot stays the read model;
  new endpoints are added only where the SPA needs data the snapshot does not
  already expose, and they follow the same bounded-redaction rules;
- accessibility target: WCAG AA, verified with the existing
  `browser_accessibility_audit` tool.

### 3. Tunnel & Cloudflare publish

- A tunnel manager surfaces the existing cloudflared/OpenAI tunnel supervisors
  in the API and SPA: start, stop, current URL, uptime, rotate credential.
- Publishing any MCP endpoint beyond loopback requires `auth.mode != none`,
  keeps the tunnel-exposure guard, and records a tunnel receipt in the audit
  log. Public MCP requires OAuth with `folderforge:read` /
  `folderforge:write` scopes plus the per-run gateway guard.
- The SPA is deployed as a static build to Cloudflare Pages via CI
  (operator-triggered); it connects back to the workstation over an
  authenticated Cloudflare Tunnel. The Pages origin never proxies tool calls.

### 4. Agent council loop

The council is a governed workflow family, not a new principal:

- roles (Architect, Security Officer, DX/UI Designer, Provisioner Engineer,
  QA/Verifier, Scribe) are workflow roles with explicit `allowedTools`, defined
  through `workflow_create` and executed by `workflow_run`;
- each cycle: discovery scan -> proposal (ADR or patch plan) -> council review
  notes -> implementation on a `council/<task>` branch ->
  `project_verify` gate (typecheck, lint, test, build) -> track-log entry in
  the shared Notion plan page;
- merges, pushes, releases, and any public exposure stay operator-approved;
- KPIs recorded per cycle: proposals merged, gate pass rate, policy incidents.

## Consequences

- The dashboard API becomes a versioned contract; the SPA must not depend on
  internal container types. See `docs/mission-control-api-contract.md`.
- Provisioned instances multiply attack surface; fleet caps, secret references,
  and per-folder boundaries are mandatory, and `provision_*` tools inherit the
  same approval classes as `process_*` and `game_*` lifecycle tools.
- Cloudflare publishing remains an explicit operator action with a security
  runbook, matching ADR-0005's "public hosting is operator-controlled" rule.
- The council cannot approve its own work: proposal authors and approvers are
  distinct, and all mutations flow through the existing approval store.

## Verification

- ADR-only change: no runtime behavior changes in this commit.
- Follow-up implementation milestones must pass `project_verify`
  (typecheck/lint/test/build) plus new unit/integration suites named in each
  phase of the tracking plan.
